# AGENTS.md

This repo is not an app codebase. It is the fresh-setup payload + repeatable setup script for a Hackberry Pi music player (MPD + myMPD + sway + waybar + PipeWire + snapclient + Euphonica flatpak).

## Layout & source of truth
- `setup-pi.sh` is the deploy entrypoint. Run **on the Pi as the target non-root user** with the payload tarred to `/tmp/setup.tar.gz` — tar from **inside** `files/` so members are `home/pi/...`, because the script extracts with `tar -C "$HOME" --strip-components=2` (stripping the template prefix `home/pi`). The `home/pi` prefix is only a tar convention; it is not the required login username. It is idempotent. See "Fresh Raspbian → music player" below for exactly what it does and does not cover.
- `setup-hyperpixel.sh` is the **display** entrypoint and must run on the Pi **before** `setup-pi.sh`: it appends an `[all]` block with `dtoverlay=vc4-kms-dpi-hyperpixel4sq` to `/boot/firmware/config.txt` (backing the file up to `config.txt.hackpi.bak`), refuses to run on non-Pi hardware, is idempotent, and needs a reboot to take effect. `OVERLAY=vc4-kms-dpi-hyperpixel4` selects the rectangular panel; `OVERLAY_PARAMS` passes the overlay's own params (`rotate=90`, `touchscreen-swapped-x-y=1`, `disable-touch=1`).
- `files/home/pi/` is the authoritative **fresh-setup template payload** — what a new machine gets, not a snapshot of an old one. Keep new files under `home/pi/` for the tar layout, but do not bake `/home/pi` or `/run/user/1000` into file contents. Use `~`, `$HOME`, `${XDG_RUNTIME_DIR:-/run/user/$(id -u)}`, systemd `%h`/`%t`, or service-relative paths so the payload works for any target user. `hackpi-backup/` and `hackpi-full-backup/` are raw snapshots of the running Pi for reference only; do not treat them as the deploy source.
- `wiremix` in `files/home/pi/.cargo/bin` is a prebuilt aarch64 binary — there is no source in this repo; don't attempt to rebuild it here. It is **gitignored** (repo keeps no binaries), so a fresh deploy needs the binary supplied separately.
- `demo/` is the promo-video pipeline (Pi screen capture → 3D keyboard render), not part of the deployed payload. See "Generating the demo video" for how a clip is recorded, re-timed, and rendered.
- `.gitignore` keeps raw Pi snapshots (`hackpi-backup/`, `hackpi-full-backup/`, `*.tar.gz`), runtime caches (`mpd/tag_cache`, `mympd/tags`, `syncthing/index-*.db`), and all private keys/certs (`*.pem`, `*.key`, `mympd/ssl`, `pin_hash`) out of the repo. **Syncthing is installed but ships no config**: the payload has no `~/.config/syncthing` at all, so `setup-pi.sh` never writes or overwrites a Syncthing config, device ID, or keys. Syncthing bootstraps its own `config.xml`/cert/key on first run and pairing is done in the Syncthing UI, so a redeploy never touches it. myMPD still regenerates its TLS cert and PIN (`ssl=true`, `pin_hash` gitignored).
- Template rules: MPD config paths use `~`; sway key commands use `exec ~/.config/...`; shell helpers use `${XDG_RUNTIME_DIR:-/run/user/$(id -u)}`; systemd user units use `%h`/`%t`; myMPD state connects to `127.0.0.1` with port `6600`; Syncthing folder paths use `~`. Do not reintroduce `/home/pi` or `/run/user/1000` into payload files.

## Fresh Raspbian → music player (what `setup-pi.sh` covers)

**Verdict:** the script installs and configures the entire software stack, but it is **not yet a complete "default Raspbian → music player" converter**. On a stock image the main blocker is that nothing makes sway the login session, so the machine boots its own compositor and the script's final `swaymsg reload` is a no-op. The sway config itself is now complete and payload-owned (no more partial-config problem). The gaps are listed below; treat them as the remaining work for a true one-shot conversion.

Deploy recipe the script assumes:
```bash
tar -C files -czf /tmp/setup.tar.gz home      # members MUST be home/pi/...
scp /tmp/setup.tar.gz setup-pi.sh pi@hackpi.local:/tmp/
ssh pi@hackpi.local 'bash /tmp/setup-pi.sh'
```
Without `/tmp/setup.tar.gz` the script falls back to `$PAYLOAD` (default `/tmp/files`) via `cp -a`, so that directory must mirror `files/home/pi/`.

What it does:
- apt-installs the stack: sway, waybar, foot, fuzzel, swayimg, imv, syncthing, pipewire/pipewire-pulse/wireplumber, mpd/mpc/mpdris2, snapserver/python3/avahi-utils, wlogout, libnotify-bin, jq, gammastep, fonts, bluez-tools/rfkill, udevil (`devmon`), network-manager, network-manager-applet. It also installs snapweb (pinned upstream release) into `/usr/share/snapserver/snapweb`.
- builds swaync **0.12.6 from source** (GTK4 rewrite) with meson/ninja, installed to `/usr`, when `swaync --version` is not 0.12.x: Debian ships only 0.11.0 (GTK3), whose mpris widget deadlocks with mpdris2 on song skips, and the tarball is checksum-pinned (`v0.12.6` GitHub archive). Build deps: valac, libgtk-4-dev, libadwaita-1-dev, libgtk4-layer-shell-dev, libgee-0.8-dev, libjson-glib-dev, libgranite-7-dev, libwayland-dev, wayland-protocols, scdoc, sassc, blueprint-compiler; built with `-Dpulse-audio=false`; the apt `sway-notification-center` package is removed first.
- builds myMPD from source with CMake (installs to `/usr`) when `mympd` is missing.
- installs bluetuith (TUI bluetooth manager) from the checksum-verified GitHub release tarball into `~/.local/bin/bluetuith` when missing.
- installs wifitui (wifi TUI) from the checksum-verified GitHub release tarball into `~/.local/bin/wifitui` when missing; `network.sh` falls back to `nmtui` if this install fails.
- installs **snapclient 0.35.0 with the pipewire player** from the pinned upstream GitHub release `.deb` (arm64/armhf/amd64 trixie, verified against the release asset digest) when `snapclient --version` is not 0.35.0 — Debian trixie's 0.31 has no pipewire player. There is **no distro fallback**: if the download/checksum/install fails, `setup-pi.sh` exits 1 rather than drifting to a client that cannot play through PipeWire. It also installs snapweb (pinned upstream release) into `/usr/share/snapserver/snapweb`.
- copies the payload configs (`waybar mpd pipewire mympd sway fuzzel wlogout swaync foot bluetuith wifitui mpDris2 snapserver snapclient`, `systemd/user`, `.cargo`, `wallpaper`) and creates `Music`, `Mixes`, `playlists`. Syncthing is apt-installed but **not configured**: the payload ships no `~/.config/syncthing`, so a deploy never writes/overwrites its config, device ID, or keys.
- unmasks PipeWire/PulseAudio user units in **both** `~/.config/systemd/user` and `/etc/systemd/user`.
- regenerates sway binds from `keys.json` and validates the assembled config with `sway -C`. The sway config itself is **payload-owned** (see below) — `setup-pi.sh` no longer seeds from `/etc/sway/config` or sed-patches it.
- installs Euphonica as a **user** flatpak with the `GSK_RENDERER=cairo` override.
- enables/starts user services (mpd, mympd, syncthing, snapclient, pipewire trio, swaync, volume-notify, audio-mode-restore) and removes dunst/mpd-notify. It disables the distro **system** snapclient/snapserver units (double-client / port-FIFO ownership) and restarts MPD so `mpd.conf` changes apply.

Gaps that block a clean first-boot conversion:
- **Nothing makes sway the login session.** The live Pi boots sway via lightdm (`/etc/lightdm/lightdm.conf`: `user-session=sway`, `autologin-user=pi`, `autologin-session=sway`, greeter `pi-greeter-wayfire`); `setup-pi.sh` never touches lightdm, so a default Raspberry Pi OS desktop keeps booting its own session (labwc on Bookworm) and the script's final `swaymsg reload` is a no-op.
- **HyperPixel4 panel setup is scripted but must run first.** `setup-hyperpixel.sh` now adds the DPI overlay to `/boot/firmware/config.txt`; run it before `setup-pi.sh` and reboot. `/boot/firmware/config.txt` itself is still not captured in `hackpi-full-backup/`.
- **`wiremix` is gitignored** → `$mod+v` is dead on a fresh deploy until the aarch64 binary is supplied separately.
- **Packages the payload assumes but never installs:** `python3` (`generate-keys.sh`, `cheatsheet-svg.py`, `brightness.py`), `git` (myMPD clone) — both present on the desktop image, absent on Lite; `wvkbd` (waybar `custom/keyboard` button), `swayidle`, `wf-recorder`/`grim`/`ffmpeg` (screen-capture workflow below), `pipewire-alsa`/`pipewire-jack`. `mixxx` is referenced by `waybar/mixxx.sh` but is not installed and not used by the current waybar config.
- **Silent failures:** `set -u` without `set -e`, plus `apt-get ... >/dev/null` and `flatpak install ... || true`, mean a failed package/build/flatpak step still prints `setup complete`.
- **State that must be re-established after a deploy:** Syncthing is not configured by setup, so a **fresh** machine generates a new device ID on first run → pair the `~/Sync`, `~/Music`, and `~/Mixes` folders once (a redeploy on an existing machine leaves Syncthing's config/keys/pairing untouched); myMPD regenerates its TLS cert and PIN (`ssl=true`, `pin_hash` gitignored); MPD needs `mpc update` since no music is seeded; a remote Snapcast server must exist on the network for Receiver mode (see "Multiroom audio" below).
- **`wlogout` power buttons run `sudo shutdown ...`** from the GUI, which needs passwordless sudo for `pi`.

## Quirks an agent will miss
- **Sway config is payload-owned.** `files/home/pi/.config/sway/config` is a complete template: it vendors a trimmed copy of the stock sway binds (collisions with `keys.json` are simply absent — no `unbindsym`, no sed patching of `/etc/sway/config`), carries the Hackberry input block, Dracula theme, window rules, workspace assigns, and the waybar/swaync/Euphonica/devmon autostarts (`nm-applet` is intentionally not autostarted), then `include ~/.config/sway/generated.conf` last so generated binds win. sway expands `~`/shell syntax in `include`/`exec`/`output` paths (wordexp), so the config needs no path rewriting. It keeps `include /etc/sway/config.d/*` because `50-systemd-user.conf` there imports `WAYLAND_DISPLAY`/`SWAYSOCK` into the systemd user environment. `setup-pi.sh` only runs `generate-keys.sh` and validates with `sway -C`.
- **Keybinds**: `files/home/pi/.config/sway/keys.json` is the single source of truth. Edit `keys.json`, then run `generate-keys.sh` (requires `jq` and `python3`) to regenerate `generated.conf` + `cheatsheet.txt` + `cheatsheet.svg`; never hand-edit `generated.conf`. Music/cheatsheet keys live only in `keys.json`; the payload sway config omits any stock bind that would collide. The Hackberry dollar key sends Shift+4 scancodes (verified via `libinput debug-events` + sway binding events), so it is bound as `$mod+Shift+4` and the stock `move container to workspace number 4` bind is disabled; when testing binds with `wtype`, send exactly what the hardware sends (here: Super+Shift+`4`), or the test gives a false negative. Toggles and launchers set `"norepeat": true` in `keys.json` (`generate-keys.sh` emits `bindsym --no-repeat`): a held key repeats past the 300ms delay and would thrash hide/show pairs. `euphonica.sh` additionally debounces presses inside 600ms so mash bursts converge to one toggle. Validate with `sway -C -c ~/.config/sway/config` after every config change.
- `keys.json` commands use `~/.config/...`, and helper scripts use `${XDG_RUNTIME_DIR:-/run/user/$(id -u)}` for sway IPC/runtime files. Verified on the live Pi: sway `exec` expands `~`, MPD expands `~` in config paths, and Syncthing expands `~` in folder paths.
- **F13 is bound on the keyboard MCU** (custom VIAL layout on the Hackberry keyboard). Re-flashing firmware loses it; snapshot the `.vil` file first. F13 triggers `cheatsheet.sh` (toggles `cheatsheet-viewer.py`, a borderless fully-transparent GTK3 window rendering `cheatsheet.svg`, so the card's rounded corners show through; the sway rule matches `app_id="cheatsheet"` and does the sizing/placement). The viewer used to be `swayimg`, but 3.8 segfaults (worse over uptime, all formats, even with `SWAYSOCK` unset, while `imv`/GTK stay fine — root cause unknown), so it was replaced; `swayimg` stays installed as a general image viewer. `for_window move` is workspace-content-relative, so the rule uses `resize set 700 520, move position 10 57` for absolute 10,100. When the viewer dies on launch, `cheatsheet.sh` posts an `ERROR:` notification instead of opening (with a PID-file check so rapid toggling stays silent).
- **PipeWire**: the stock Pi image masks pipewire/pulseaudio user units in BOTH `~/.config/systemd/user` and `/etc/systemd/user`. Unmask both or MPD audio (pipewire output) and snapclient break.
- **Multiroom audio (Snapcast)**: `$mod+x` and the waybar `custom/audio` button run `~/.config/sway/audio-mode.sh` (`pick`, or `set off|receiver|broadcast|group`, `listen <host:port>|auto`, `status [--waybar]`, `list`, `restore`). Modes live in `~/.config/sway/.audio-mode` (one word, default off); the remote host lives in `~/.config/snapclient/env` (`SNAPCLIENT_OPTS=--host <h> --port <p>`, comment-only = Avahi discovery). **Off** (default) = MPD → PipeWire local playback only, snapserver and snapclient stopped; **Receiver** = MPD → PipeWire, snapserver stopped, snapclient listening to a remote server; **Broadcast** = MPD → PipeWire + fifo `Multiroom` → `snapserver` (no local client); **Group** = MPD → fifo only, local snapclient `--host 127.0.0.1 --port 1704`, every room sample-synced (PCM `chunk_ms=20`, `buffer=150`, ~200 ms). `snapserver.service` (payload user unit) is deliberately **never enabled** — only the picker/waybar start it and Off/Receiver stop it, so the Pi advertises nothing when idle; `audio-mode-restore.service` re-applies the saved mode (including Broadcast/Group) at boot after MPD. The MPD `fifo` output `Multiroom` (`format "48000:16:2"`, `enabled "no"`) must be enabled only after snapserver is up and disabled before it stops. Setup adds `snapserver python3 avahi-utils`, disables the distro **system** snapclient/snapserver units, removes `/tmp/snapfifo`, and restarts MPD (a `start` is a no-op). Gotchas: the payload unit uses `--player=pipewire`, which needs the pinned upstream snapclient 0.35.0 `with-pipewire` .deb (`setup-pi.sh` installs it; Debian trixie's 0.31 has no pipewire player and exits 1 with `No audio player support for: pipewire` the moment it connects to a server); mode switching restarts snapclient so the unit sets `StartLimitIntervalSec=0` (default 5-starts/10s rate limit shows up as `Result: start-limit-hit`); `systemctl show -p Environment` omits EnvironmentFile values (read `/proc/$(systemctl --user show snapclient -p MainPID --value)/environ`); on the ~260-DPI panel, fuzzel `dpi-aware=auto` renders pickers wider than 720 px, so the audio pickers pass `--dpi-aware=no --font "JetBrains Mono:size=13"`; `group` clears its `127.0.0.1` env override when leaving the mode. snapweb is served at `http://<host>:1780` while the server runs, and it needs `[http] doc_root = /usr/share/snapserver/snapweb` in the payload `snapserver.conf` (the compiled default is empty because `-c` replaces `/etc/snapserver.conf`, so without it `:1780` serves snapserver's built-in placeholder page); the waybar module uses `"signal": 8` and `audio-mode.sh` runs `pkill -RTMIN+8 -x waybar` for instant indicator refresh (no `interval` is configured, so the signal is the only refresh path); `snapclient.service` sets `PartOf=pipewire.service` so the client restarts with PipeWire and is never orphaned; Avahi can hand the client an IPv6 address while snapserver binds IPv4 by default (upstream #715 → `Connection refused`), so receiver mode always passes an explicit `--host` (or set `bind_to_address = ::` in `snapserver.conf`); **remote receiver switching is not implemented** — Snapcast has no server-switch protocol (a server controls its own connected clients via JSON-RPC but cannot move a client to another server), so a receiver is pointed at a sender locally once via `Listen to...`; a receiver-side `snapswitch` agent was designed and deliberately deferred. Other rooms join while the Pi is in Broadcast/Group with any Snapcast client (`apt install snapclient` then `snapclient --host hackpi.local`, or the Windows/macOS/Android/iOS Snapcast apps pointed at `hackpi.local:1704`). Verified end-to-end 2026-10-09: picker (Super+X), off/receiver/broadcast/group cycle, loopback PCM capture, boot restore in group, full smoke suite green (142 pass).
- **Audio output switcher**: `$mod+d` runs `~/.config/sway/device.sh next`, which cycles PipeWire's default sink through the connected sinks (parses `wpctl status`, applies `wpctl set-default`) and reports each switch with a synchronous `Audio output` notification (`2/2 -> WH-1000XM4 Headphones`). The same script takes `prev`, `pick` (fuzzel picker) and `list` (`id<TAB>default<TAB>title` rows, used by the smoke test). The notification center moved from `$mod+d` to `$mod+Return` (`notifications.sh`).
- **Notification miniplayer**: swaync's `mpris` widget is first in `widgets` with `widget-config.mpris` (`image-size: 96`, `autohide: false`, `show-album-art: "when-available"`, `loop-carousel: true`) and `control-center-height: 480`, so MPD sits at the top of the control center; `.widget-mpris` is styled in Dracula colors in `swaync/style.css`. It only works because `mpdris2` (apt) bridges **user** MPD onto the session bus as `org.mpris.MediaPlayer2.mpd` — `setup-pi.sh` detects the distro-provided user unit by name (`mpDris2.service` on Ubuntu; the name varies across distros) and enables/restarts it. The live Pi runs **swaync 0.12.6** (source-built GTK4), so the 0.12-only mpris keys are live: `autohide`, `show-album-art`, `loop-carousel`, and `blacklist` (regex against the bus name; still supported in 0.12.6). `image-size` still works but is deprecated in favor of the CSS root variable `--mpris-album-art-icon-size`; `image-radius` and `blur` no longer exist in 0.12 (removed from the payload config — radius comes from the CSS `border-radius`). `autohide: false` keeps the widget visible even with empty metadata. Query MPRIS state with `busctl --user call org.mpris.MediaPlayer2.mpd /org/mpris/MediaPlayer2 org.freedesktop.DBus.Properties Get ss org.mpris.MediaPlayer2.Player PlaybackStatus` — `PlaybackStatus`/`Metadata` are on the `Player` interface, and mpDris2 raises a `KeyError` if you ask the wrong interface. Read panel state with `busctl --user call org.erikreider.swaync.cc /org/erikreider/swaync/cc org.erikreider.swaync.cc GetVisibility` (and `NotificationCount` for the count; `GetVisibility` exists on both 0.11 and 0.12); `swaync-client -s` is a never-exiting subscription, not a status read, and `-cp`/`-op` are the deterministic close/open commands. **mpdris2's own track-change notifications stay disabled** (`~/.config/mpDris2/mpDris2.conf`, `[Bling] notify = false`, payload-owned): swaync 0.11.0's mpris widget made a **synchronous** D-Bus `Get` inside its `PropertiesChanged` handler while mpdris2 (single-threaded) made a blocking `Notify` call to swaync on every song change — skipping a song deadlocked both (swaync froze, `notify-send` blocked, miniplayer buttons dead; pause was safe because it triggered no mpdris2 notification; symptom: hang until mpdris2's Notify timed out (~25s) with `Failed to show notification: g-io-error-quark: Timeout was reached` in `journalctl --user -u mpDris2`, main thread stuck in `g_dbus_connection_send_message_with_reply_sync` under `gdb -p $(pgrep -x swaync) -batch -ex "thread apply all bt"`). swaync 0.12 made these calls async, but `notify = false` stays: mpdris2's per-song popups would duplicate the miniplayer.
- **myMPD**: no Debian package — must be built from source with CMake (handled in `setup-pi.sh`); installed to `/usr`, runs as a user service against user MPD.
- **Euphonica** is a user-scope flatpak (`flatpak --user run io.github.htkhiem.Euphonica`); it must be installed with `--user`, and sway autostarts it on workspace `1:Music`.
- **Workspaces**: Euphonica + `wiremix` are assigned to `1:Music`, `firefox` to `2:Browser` (assigns in sway config, added by `setup-pi.sh`). The launcher helpers (`euphonica.sh`, `wiremix.sh`, `browser.sh`) switch to the target workspace before launching, and `$mod+g` opens the default browser. The terminal (`$mod+tab`) always opens floating on the current workspace.
- **Bluetooth**: `setup-pi.sh` installs `bluez-tools` + `rfkill`, enables `bluetooth.service`, and adds the user to the `bluetooth` group (re-login needed). `$mod+b` toggles a floating foot window running **bluetuith** (`bluetooth.sh`; `app_id=bluetooth`, `--font "JetBrains Mono:size=13"`, 600x600 sway rule) — a TUI bluetooth manager (pair `p`, connect `c`, trust `t`, remove `d`, scan `s`, discoverable `S`, power `o`, **audio profiles `A`** = the A2DP/HSP switch that `bluetoothctl` makes painful, `Alt+m` menu, `?` help). bluetuith has no Debian package and the repo keeps no binaries, so `setup-pi.sh` downloads the GitHub release tarball for `uname -m` (aarch64→arm64), verifies it against the release `checksums.txt`, and installs `~/.local/bin/bluetuith` — a deploy needs network, and on failure `bluetooth.sh` falls back to `bluetoothctl`. Config is `~/.config/bluetuith/bluetuith.conf` (HJSON): `adapter-states: "powered:yes,pairable:yes"` + a Dracula theme. Gotchas: `MenuBar` is a **background** color (never the same color as `Adapter`/`MenuItem` text, or the menu bar renders blank), `Background: default` is rejected (use `transparent`), a stray line in the file aborts startup with `Found EOF while looking for a key name`, and `receive-dir` is left unset because `~` is not expanded — the launcher exports `BLUETUITH_RECEIVE_DIR=$HOME/Downloads` instead. PipeWire plays through connected devices via `libspa-bluetooth`.
- **Network UI**: `setup-pi.sh` enables `NetworkManager` and installs `wifitui` from the pinned GitHub release (`v0.13.0`, checksum-verified) into `~/.local/bin/wifitui`. `$mod+n` and the waybar `custom/network` button run `~/.config/sway/network.sh`, which toggles a floating `foot --app-id network` window at 600x600 with `--font "JetBrains Mono:size=15"` and `WIFITUI_THEME=$HOME/.config/wifitui/theme.toml`. `nm-applet` remains installed but is not autostarted and the waybar `tray` module is gone; `nmtui` is the fallback when `wifitui` is unavailable.
- MPD runs as a **user** systemd service (not system), music dir is `~/Music` (MPD library root), playlists `~/playlists`, audio output is `pipewire`. Music arrives via syncthing (`Sync` → `Music`, `Mixes`).
- Waybar custom modules exec shell scripts in `files/home/pi/.config/waybar/` (mixxx launch, now-playing via D-Bus/RIS, keyboard, network, power menu); waybar must be reloaded with `pkill -USR1 -x waybar` after config edits.
- **Brightness**: the HyperPixel4 panel backlight is on/off only (`/sys/class/backlight/backlight/max_brightness` = 1; hardware dimming is the physical button). Waybar's backlight module is removed and there is **no brightness keybind** (`$mod+b` is bluetooth; stock `splith` is dropped). `~/.config/sway/brightness.py` (gammastep software dimmer) and `gammastep` remain installed — run it manually if needed: `foot -e python3 ~/.config/sway/brightness.py` or `brightness.py --set <percent>`.
- **Volume notifications**: `~/.config/sway/volume.sh` handles the sway volume keybinds and sends synchronous notifications; `volume-notify.service` runs `~/.config/sway/volume-notify.sh` to notify when PipeWire's default sink volume changes elsewhere. Notifications are not capped at 100%.

## Verification on the Pi
- After changes: copy payload → run `setup-pi.sh`, then `swaymsg reload` and `pkill -USR1 -x waybar`.
- On a fresh image, additionally check: the login session is actually sway (`swaymsg -t get_version`), `~/.config/sway/config` is the payload template (trimmed stock binds + `include ~/.config/sway/generated.conf`) and passes `sway -C -c ~/.config/sway/config`, the HyperPixel4 is the active output (`swaymsg -t get_outputs`), syncthing is paired, and myMPD answers on `https://hackpi.local:8443` with the regenerated PIN.
- If a waybar restart makes the top bar disappear, reboot the Pi (`sudo shutdown -r now`) and wait for SSH to return before continuing; do not keep retrying `pkill` or `swaymsg exec waybar` over SSH.
- Key services: `systemctl --user status mpd mympd syncthing snapclient snapserver pipewire pipewire-pulse wireplumber volume-notify`; test playback with `mpc toggle` / `mpc play`.
- Multiroom: `bash ~/.config/sway/audio-mode.sh list` shows the mode; in Broadcast/Group prove audio with `timeout 3 snapclient --host 127.0.0.1 --player=file:filename=/tmp/cap.raw,mode=w && test -s /tmp/cap.raw`; `snapserver` must be inactive in Receiver; snapweb answers on `curl -sI http://127.0.0.1:1780/` while the server runs. The smoke-test `multiroom` stage covers the full cycle and the picker.

## Taking screen videos
- Use `wf-recorder` on the Pi for Wayland screen recordings. It is installed on the live Pi but **not** by `setup-pi.sh` — install it first: `sudo apt-get install -y wf-recorder grim ffmpeg`.
- GUI recording commands need the same Wayland environment as other sway tests:
  ```bash
  export XDG_RUNTIME_DIR=/run/user/1000
  export WAYLAND_DISPLAY=wayland-1
  export SWAYSOCK=$(ls /run/user/1000/sway-ipc.*.sock | head -n1)
  ```
- Record a short action with continuous frames so transient window mapping is captured:
  ```bash
  ssh pi@hackpi.local 'bash -s' <<'EOF'
  export XDG_RUNTIME_DIR=/run/user/1000
  export WAYLAND_DISPLAY=wayland-1
  export SWAYSOCK=$(ls /run/user/1000/sway-ipc.*.sock | head -n1)

  timeout 5 wf-recorder -f /tmp/recording.mp4 -D -r 15 >/tmp/wf.log 2>&1 &
  rec_pid=$!
  sleep 1

  # Trigger the action being recorded, for example:
  swaymsg "exec /home/pi/.config/sway/cheatsheet.sh"

  sleep 3
  kill -INT $rec_pid
  wait $rec_pid || true
  EOF
  ```
- Pull the video to the workstation and extract frames for visual inspection:
  ```bash
  scp pi@hackpi.local:/tmp/recording.mp4 /tmp/opencode/
  mkdir -p /tmp/opencode/recording_frames
  ffmpeg -v error -i /tmp/opencode/recording.mp4 -vf fps=5 /tmp/opencode/recording_frames/frame_%02d.png
  ```
- Use `-D` (`--no-damage`) when recording short UI transitions; without it, `wf-recorder` may only emit frames when the screen changes and can miss the first mapped window state.
- Use `-r 15` for a small, inspectable frame rate. Use `-g x,y WxH` only when a cropped region is needed; full screen is `720x720`.
- Stop `wf-recorder` with `kill -INT`, not `kill -9`, so the MP4 is finalized cleanly.
- For stills, use `grim /tmp/screenshot.png`, then pull it to `/tmp/opencode/`.

## Generating the demo video
`demo/` is the promo-video pipeline, separate from the Pi payload. It has two stages: record the real Pi screen, then render the 3D Hackberry keyboard with that recording as its screen texture.

Stage 1 — record on the Pi (`demo/overlay_demo.sh`):
- Copy both files first: `scp demo/overlay_demo.sh demo/swaymp-touch.c pi@hackpi.local:/tmp/`, then `ssh pi@hackpi.local 'bash /tmp/overlay_demo.sh'`. It plays `ENOENT/Sinbiotic EP/enoent_hopscotch_16bitwav_master.wav` from `START_AT=40`, fires timed `Super+P/K/J`, sweeps volume with 10 `Super+I` then 10 `Super+O` (`volume.sh` steps 5%, so 10 presses = 50 points), opens `fuzzel` with `Super+Space`, then opens foot with `Super+Tab` and types `mpc status` / `exit` char-by-char (per-char `TYPE` marks drive per-key glow in the render), then touches the waybar `custom/cheatsheet` button. Bluetooth/network beats were removed in v4.
- All demo popups use `--hint=string:x-canonical-private-synchronous:swaymp-demo` so each new popup **replaces** the previous one (swaync otherwise keeps them ~6s and they stack). The pointer is parked in the bottom-left dead corner before recording and after the queue touch so no widget tooltip lingers.
- Output: `/tmp/swaymp-overlay.mp4` (wf-recorder + PipeWire audio) and `/tmp/swaymp-overlay.marks`. **The `.marks` file is the source of truth for `EVENTS` in `index.html`** — copy the timings, don't guess them.
- Needs `wf-recorder`, `wtype`, `notify-send`, `mpc`, `wpctl`, `swaymsg`, `gcc`, and passwordless sudo: `demo/swaymp-touch.c` is a uinput pointer injector (compiled to `/tmp/swaymp-touch`, run via `sudo`) used because the cheatsheet beat is a *pointer* click on the waybar button (~`(82, 20)` on the 720x720 panel), not a keypress. Sway pointer accel is set `flat 0` for the touch and restored to `adaptive 0` after, otherwise the injected pointer drifts.
- There is **no F13 keycap in the 3D model**, so cheatsheet beats must be shown on the Pi screen only — do not add a keycap event for them.

Stage 2 — render on the workstation (`demo/make.sh`):
- Prerequisite: `demo/swaymp-overlay.mp4` is **not committed** (gitignored via `demo/*.mp4`); copy it from the Pi (`scp pi@hackpi.local:/tmp/swaymp-overlay.mp4 demo/`) before rendering. The committed `demo/frames/` are the render texture, but `extract_frames.sh`/`mux.sh`/`make.sh` still need the clip locally (frames regeneration + audio mux).
- `extract_frames.sh` → `demo/frames/` (12fps, 720x720 JPEGs; committed, they are the screen texture). This Chromium decodes `<video>` to black pixels for WebGL/canvas, so the page uses pre-decoded JPEGs instead of a `VideoTexture`.
- `sanitize_video.sh` and `sanitize_frames.sh` are currently no-ops (no sensitive windows since the Bluetooth/network beats were removed in v4); `SENSITIVE` in `index.html` is empty. Keep the mechanism for future beats, and keep all three in sync with `EVENTS` if windows return.
- The render backdrop is `demo/bg.jpg` (Unsplash photo by Pat Hayden, same file as the Pi wallpaper `files/home/pi/wallpaper/wallpaper.jpg`), cover-fit to the portrait frame. The key-press `PointLight` must stay tight (`distance 70`, low height) — three.js legacy falloff is ~linear, so a wide light washes neighboring keys amber and reads as wrong keys lighting up.
- `demo/embed.mp4` is the small GitHub-embeddable cut of `kb_final.mp4` (480px, CRF 23, `+faststart`); it is the **only** committed video (`!demo/embed.mp4` in `.gitignore`). Regenerate it after any re-render.
- serves `demo/` on `127.0.0.1:7171`, runs `record.py` through `browser-harness` (attaches to Chromium CDP at `BU_CDP_URL`, default `http://127.0.0.1:9333`, auto-launching a browser if none is running) to capture the three.js canvas via the page's own `MediaRecorder` → `kb_final.webm`.
- `mux.sh` maps the canvas video with the **source clip's audio** → `kb_final.mp4`. Both start at t=0, so audio stays in sync; `-shortest` trims the capture tail.

Coupling rules (the failure modes):
- `index.html` `EVENTS` must match the `.marks` timings, and `record.py`'s `KB_DUR` must be **≥ the source clip duration** or the final video is truncated.
- `index.html` sizes the frame preload from `vid.duration` (no hardcoded frame count) with a 400-frame fallback after 4s.
- `extract_frames.sh` skips extraction when `frames/f_001.jpg` exists, but still runs `sanitize_frames.sh` unless `frames/.sanitized` exists — delete `demo/frames/`, `demo/frames/.sanitized`, and `demo/.swaymp-overlay.sanitized` whenever the source clip changes, or the render keeps the old screen.
- `kb_final.webm` / `kb_final.mp4` are build outputs; do not commit videos. The source clip `demo/swaymp-overlay.mp4` is also gitignored (`demo/*.mp4`) — it is a local-only artifact supplied from the Pi, not a tracked file.
- If `make.sh` is interrupted, the `http.server` on 7171 and the harness Chromium can be left running; the blob download streams in 4MB chunks, so a long clip legitimately takes several minutes.
